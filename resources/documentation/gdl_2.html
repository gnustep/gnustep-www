The Model

The model represents the organization of your Application Objects' classes and how it relates to the data in the database. It describes what is the relation between these objects rather than describing the strict organization of your database tables. The model does not necessary follow the exact organization of your database. You can imagine different models based on a database structure, depending on your application demands.

You describe the model using the Entity-Relationship modeling. Entity-Relationship modeling uses entities, attributes and relationships to describe the organization of the data. In a relational database, entities represent tables and an entity's attribute represent a table's column, though not all the columns can be mapped in attributes for a given entity.

If we have the Person table in a database, we can associate it with the Person entity. If the table has firstName, lastName and picture as columns we can associate those columns attributes with the same names.

You can create attributes that don't exist in the entity's table. For example you might want to compute the anual salary of a person from its month salary by multiplying it by twelve. These attributes are called derived attributes.

GDL extends the usual Entity-Relationship model by allowing you to add to an entity attributes that are part of another entity. These attributes are called flattened attributes.

In the Entity-Relationship model in addition to entities and attributes you also describe relationships between entities. A relationship describes the logical relation that exists between two entities. In our example the Department entity has a relationship of which Persons belong to that department.

Application Objects are the basic units on which the database operations are made. Retrieving, updating, inserting and deleting operations are perfomed on Application Objects. Each Application Object class should be described by an entity. So an entity has associated with it the Application Object class used by the database level to create instances.

The attributes of an entity are mapped into instance variables of Application Objects. The instance variables could be of an object type or other elementary Objective-C types. Since values are returned by the adaptor level in a dictionary and they are of an object type, GDL automatically translates object values to an elementary Objective-C type if needed.

A model is described in a file in the property-list format. The model file is read at run-time when the application creates the database or adaptor objects. Your program generally doesn't manipulate the model directly unless you want to change it dinamically. The format of the model file is described in the further sections.

The classes used to represent a model are EOModel, EOEntity, EOAttribute, EORelationship and EOJoin. In the following we will detail the model classes.

EOModel

The EOModel class represents the model of all your Application objects; generally a program will just have a single model, but it is possible to have multiple models if desired. For example, an organization may put Payroll and Human Resource Application Objects together into a single model because of the large overlap in the two business processes. However, another organization may wish to separate them into two models; each model only containing Application Objects which represents the information needed from the other model. Using two separate models allows you to explicitly model what Payroll information Human Resources is allowed to see and vice-versa.

Loading a Model File

Models can be stored in text files and loaded upon execution of a program. Storing the model in a file allows external programs to be used for parsing and maintaining your models separate from your programs. The GNUstep Interface Modeller application is an example.

The -initWithContentsOfFile: method is used to initialize a newly allocated EOModel instance with the contents of a file; the following code sample shows its use. 

NSString *modelPath;
EOModel *humanResourceModel;

modelPath = [EOModel findPathForModelNamed: @"HumanResource"];
humanResourceModel = [[EOModel alloc] initWithContentsOfFile: modelPath];

The +findPathForModelNamed: method searches a series of directories to find the model file. It first searches the application's main bundle directory, then the user's home library directory (~/Library/Models), and lastly the GNUstep Database Library directory ($GNUSTEP_DB_LIBDIR/Models). Other directories may be searched based upon your local GNUstep setup. +findPathForModelNamed: attaches the extension `.eomodel' onto the name to produce the complete filename.

Creating a Model from the Database Schema

The EOAdaptorChannel class has the methods -describeTableNames and -describeModelWithTableName: that can be used to construct a model based upon the current database schema. It is necessary for you to have a valid connection to the database before using these methods; the following code sample shows how to create a model for all of the tables in the database. 

EOAdaptorChannel *myChannel;   /* this already exists */
EOModel *myModel;

myModel = [myChannel describeModelWithTableName:
                [myChannel describeTableNames]];

The model may or may not be able to construct relationships between tables based upon whether that data is available from the database schema.

Programmatically Creating a Model

It is also possible to construct a model programmatically; an example where this may be necessary is if the actual model is dependent upon data values in the database and cannot be know ahead of time.

Use -initWithName: to initialize an EOModel instance and assign it a name. Then use -addEntity: to add EOEntity instances to your model. You must also set the name of the adaptor class with -setAdaptorName: and set the connection dictionary with -setConnectionDictionary: before you attempt to use the model.

Merging Models

-incorporateModel: is a method that can be used to completely incorporate one model with all of its entities into a receiving model. The method returns YES if successful or NO if there are conflicts between the two models. Possible conflicts are identically named elements that do not match in structure or if the models use different adaptors. Incorporation of a model does not affect the connection dictionary of the receiving model.

The model that is incorporated is disposed, so if you wish to still use that model after incorporation; then create a copy of the model and incorporate that copy.

Property List Representation of a Model

As indicated earlier, models are stored as property lists in text files. A property list is a textual representation of NSDictionary, NSArray, NSString, and NSData object.

You can request a model to return its complete schema as a property list (within an NSString) with -modelAsPropertyList; the following code sample shows how to write out a model to a file. 

EOModel *myModel;  /* this already exists */
NSString *propertyList;

propertyList = [myModel modelAsPropertyList];
[propertyList writeToFile: @"TheModel.eomodel" atomically: YES];

EOModel also has the -initWithPropertyList method which initializes a newly allocated EOModel with the contents of a property list; the following code sample shows how to create a copy of a model. 

EOModel *originalModel;  /* this already exists */
EOModel *modelCopy;

modelCopy = [[EOModel alloc] initWithPropertyList:
                [originalModel modelAsPropertyList]];

Additional EOModel Methods

-path returns the full path of the file used to initialize the EOModel instance; this includes the directory, filename, and file extension. the method returns nil if the model was not initialized from a file.

-name returns the model name.

-adaptorName returns the name of the adaptor class for the model.

-connectionDictionary returns the connection dictionary associated with the model; the returned dictionary is immutable so you must use an appropriate -setConnectionDictionary: method in EOModel or EOAdaptor to change the connection dictionary.

-entity returns an NSArray containing all of the model's EOEntities.

-entityForObject: returns the entity for an Application Object.

-entityNamed: returns the EOEntity in the model with the specified name.

-referencesToProperty: returns an array of all properties, such as EOAttribute and EORelationship, that reference the property in the model.

-userDictionary: and -setUserDictionary: are used to return and set the dictionary of user data; this dictionary can be used by the application to store any auxiliary information related to the model.

Attributes

An attribute is an instance of the EOAttribute class. An attribute could be simple, derived or flattened.

A simple attribute is one that maps directly over a column from the table. firstName, lastName and picture are examples of simple attributes.

A derived attribute is an expression that depends on other attributes from entity. For example salary * 12 is a derived attribute.

A flattened attribute is a mapping of an attribute from another entity. If the Department entity has a to-one relationship to the Person that is the chief of department, then we can arrange to have two flattened attributes firstName and lastName that represent the name of the chief. In order to be able to do this we have to create a to-one relationship to the Person entity. see section Relationships for more information about relationships. It is an error to specify flattened attributes using relationships that are not to-one.

You can declare a flattened attribute by specifying the whole path to the attribute. For example if toBoss is the relationship in Department that specifies the chief of the department; then we can define the two above flattened attributes by toBoss.firstName and toBoss.lastName.

Flattened attributes can be defined over several relationships. Suppose we have three entities A, B and C and the to-one relationships toB in A and toC in B and c is an attribute of C. Then we can define in A a flattened attribute c whose definition is toB.toC.c. Note that both relationships must be defined as to-one.

If the attribute is simple you should specify the name of the column it represents and the external type of the column. The external type is dependent on the database server you use so if you want to use the model with another database server you have to change the type accordingly.

When the adaptor retrieves records from a table corresponding to an entity, it creates values for each attribute from entity. These values are instances of the class you specify for attribute. If this class is NSNumber you can also specify the type of the value. When the adaptor executes other operations such as updates or insertions, it converts the values from dictionaries into the proper values needed by the database as specified in the external type. You can also create your own value classes and interpret the value type as you wish.

An attribute has a name associated with it which identifies it within its entity. The attributes names have to be unique within an entity. If the attribute is simple the name could be different than the column name it represents.

A simple attribute is specified in the model file like below: 

{
    columnName = first_name;
    externalType = varchar;
    name = firstName;
    valueClassName = NSString;
}

A derived attribute is specified like in the below example. The names that appear as attributes in the definition should be valid attribute names even if they are from other entities as long as the relationships path to them exist. Any other names that appear are left unmodified. The names that can appear in the definition should be attribute names and not external names, otherwise the generated SQL SELECT expression can be incorrect. 

{
    definition = "lastName + ',' + firstName";
    externalType = varchar;
    name = Name;
    valueClassName = NSString;
}

Finally, a flattened attribute is declared like this: 

{
    definition = toBoss.lastName;
    name = BossName;
}

Relationships

A relationship expresses the relation that exists between two entities. In our previous simple model each department has a chief. This relation is figured out by a relationship between Department and Person, named toBoss.

When you define a relationship you have to decide what is the source entity and what is the destination entity. You also have to specify pairs of attributes from the two entities that are linked together. In our example we can link together the personId attribute in the Department entity and the personId attribute from the Person entity.

You can use whatever attributes you want to specify the link between the two entities. However these attributes are usually chosen very carefuly because they have to link unique objects; the attributes from the destination entity are usually the primary key of the entity (see section Primary Keys). When the attributes from the destination entity are primary keys the attributes from the source entity are called foreign keys; the values for these attributes are the values of the primary keys from the destination entity.

Joins

The link between the source and destination attributes is specified as we seen above by a set of attributes pairs. Each pair of attributes together with the join operator and the join semantic, about which we will discuss later, is called join.

The join operator specifies the relation between the two attributes of the join and can be one of the less than, less than or equal to, greater than, greater than or equal to, equal to and not equal to operators. The relation between the source and destination attributes through the join operator is called join condition.

The join semantic tells how the tuples from the two entities are selected. The possible join semantics are (1):

  • inner join: selects only the tuples that satisfy the join condition.
  • full outer join: selects all the tuples even if the join attributes do not satisfy the join condition.
  • left outer join: selects only the tuples whose source records have no corresponding destination records.
  • right outer join: selects only the tuples whose destination records have no corresponding source records.

Relationship Cardinality

When you define a relationship it exists only between the source and destination entities. If you need a reverse relationship you should define another one in the destination entity. For example the Person entity has a relationship toDepartment to the Department. Another relationship toPersons exists between the Department and Person entities.

An important property of a relationship is its cardinality. This property is given by the number of destination records that corespond to a given source record. If only one destination record is associated through the join to a source record for all the records in the source entity, the relationship is called to be a to-one relationship. In our example each Person has a unique Department in which he or she works so the toDepartment relationship is a to-one relationship.

If more than one records in the destination entity are associated with a source record for at least one record in the source entity, then the relationship is called a to-many relationship. The toPersons relationship in the Department entity is an example of a to-many relationship.

Flattened Relationships

The relationships we have seen so far were simple relationships. Each one has a source entity and a destination entity and has joins that link these entities. The GDL model allows you to specify relationships that link two entities using other relationships. These relationships are called flattened relationships.

Suppose we have another entity called Facility which tells what is the building where a department is. In a building we can possibly have more the one department but we consider a department to be in a single building. We can model this by adding a relationship toFacility in the Department entity and a toDepartments relationship in the Facility entity. Now if we want to know in which building a Person is, we can create a flattened relationship from Person to Facility called toFacility to be toDepartment.toFacility. This definition specifies the whole path to follow to reach the Facility entity.

A flattened relationship has the cardinality depending on the relationships that compose it. If all the relationships are to-one then the relationship is also to-one. If there is at least one relationship that is to-many, the flattened relationship is to-many.

Many-to-many Relationships

In many problems is necessary to create some many-to-many relations between two entities: each record from an entity has associated with it more than one records from the other entity. For example suppose we have the Project entity who keeps all the projects in work. A Project has many people who work on it. Also suppose that a people can be involved in more than one project.

To allow such a behavior another entity has to be introduced. This entity keeps two to-many relationships: one to first entity and one for the second entity. The source attributes of these relationships are the primary keys of the entities. In our example we can introduce the PersonProject entity whose attributes are the personId and projectId attributes. The related relationships are toPerson and toProjects respectively.

Reflexive Relationships

You can define relationships whose source and destination entities are the same. This kind of relationships is called reflexive relationships. For example we can define a relationship toBoss whose foreign key bossId is the id of the person who is the chief of a given person. The persons who don't have a chief have the bossId attribute set to NULL to indicate this.

A person who is chief can in turn have its own chief. This way the dynamic chain of chiefs can be arbitrarly long and is not limited to the static definition of the toBoss definition.

The reflexive relationships are not limited to to-one relationships; to-many reflexive relationships can be imagined as well.

Describing Relationships

Relationships are described for a given entity. In GDL the class used to represent relationships is EORelationship. See the description of this class for more info.

In the model file all the relationships of an entity can be accessed from the entity's dictionary under the key relationships. The value associated is an array of relationships.

A relationship has the following properties:

  • the name of relationship under the key name (the value should be NSString).
  • the name of the destination entity under the key destination (the value should be NSString).
  • an array of join descriptions.
  • a boolean that specifies if the relationship is to-many or not under the key isToMany (the value should be Y or N).

A join description is a dictionary containing the following properties:

  • the source attribute name under the key sourceAttribute (the value should be a NSString).
  • the destination attribute name under the key destinationAttribute (the value should be a NSString).
  • the name of the join operator under the key joinOperator. The possible values for this are:
    • EOJoinEqualTo,
    • EOJoinNotEqualTo
    • EOJoinGreaterThan
    • EOJoinGreaterThanOrEqualTo
    • EOJoinLessThan
    • EOJoinLessThanOrEqualTo.
  • the name of the join semantic. The possible values for this are:
    • EOInnerJoin
    • EOFullOuterJoin
    • EOLeftOuterJoin
    • EORightOuterJoin

Example: 

relationships = (
    {
        destination = Department;
        isToMany = N;
        joins = (
            {
                destinationAttribute = deptId;
                joinOperator = EOJoinEqualTo;
                joinSemantic = EOInnerJoin;
                sourceAttribute = deptId;
            }
        );
        name = toDepartment;
    },
    {
        destination = Person;
        isToMany = N;
        joins = (
            {
                destinationAttribute = personId;
                joinOperator = EOJoinEqualTo;
                joinSemantic = EOInnerJoin;
                sourceAttribute = bossId;
            }
        );
        name = toBoss;
    }
);

If the relationship is flattened you have to specify only the name of the relationship and its definition. The definition of relationship is specified under the key definition.

Example: 

relationships = (
    {
        definition = toDepartment.toFacility;
        name = toFacility;
    }
);

A join is represented in the program by instances of EOJoin class. See a description of this class for more information.

Entities

Entities describe how the records from a specific table from database map to Application Objects. An entity is described in GDL by an instance of EOEntity class. An entity has some attributes that describe the logic organization of data in a particular table and how is this organization represented in the Application Object as well as other internal attributes.

  • the name of the entity
  • the class name of the Application Object
  • the name of the database table
  • its attributes
  • its relationships
  • the attributes used as primary keys
  • the attributes used as class properties
  • the attributes used for locking

Primary Keys

When you work with records in a table you usually want to make them distinct each other in order to later identify them uniquely. To do this you specify a set of attributes that make the records distinct. These attributes are called primary keys.

For example the personId attribute from the Person entity can be used as primary key if its value is different for all the persons.

You should specify as primary keys only the minimal set of attributes that guarantees the records are distinct. Redundant attributes does not influence the uniquess of records but affect the speed of uniquing in the database level. Also you should avoid specifying as primary keys attributes having as types large binary data or big strings.

Class properties

All the EOAttributes in an EOEntity are usually needed to be represented in an Application Object. There are times however when you don't want to have an attribute represented in an Application Object because you use it only for locking or for specifying a relationship.

You can specify a set of class properties that are to be represented in an Application Object. Only those attributes marked as class properties are represented in Application Objects.

Locking Attributes

When the database level is configured to use optimistic locking (see section Uniquing), it uses the the attributes specified as locking attributes in the qualifier of UPDATE operation to modify an Application Object. If the record in database corresponding to the Application Object has some of these attributes modified the UPDATE operation fails.

The attributes used for locking should not be necessary specified as class properties. The locking attributes are anyway retrieved from the database and if they are not class properties they will not be seen by the Application Object.

Describing Entities

An entity description is a dictionary containing these entries under the following keys:

  • name -- the name of the entity
  • className -- the class name of the Application Object
  • externalName -- the name of the table from the database
  • userDictionary -- a dictionary that can be interpreted by the user application (optional)
  • attributes -- an array of EOAttribute descriptions
  • primaryKeyAttributes -- an array of attributes names used as primary keys
  • classProperties -- an array of attributes names used as class properties
  • attributesUsedForLocking -- an array of attributes names used for locking (optional if you don't use uniquing)
  • relationships -- an array of EORelationship descriptions (optional)

When you have to specify the attribute names in arrays you should use the name of the attribute not the external names.

A Complete Model

The model contains all the information we described so far. The class whose instances are used to describe models is EOModel. A model is described by a dictionary in which the following keys have meaning:

  • EOModelVersion -- the version of the model file (current version is 1)
  • adaptorName -- the name of the adaptor
  • adaptorClassName -- the class name of the adaptor class (inherited from EOAdaptor)
  • connectionDictionary -- a dictionary that contains information specific to each adaptor
  • entities -- an array that contains all the entities

Resolving cycles within your model. A garbage collector

While describing complex data structures you can do relatively easily cycles within your model. For example if we want to know what are the people who work into a Department we need a relation from Department to Person. In our model this creates a local cycle.

Because of the OpenStep Foundation ownership policy these kind of cycles make the objects implied in them to be leaks, because they never get deallocated.

To solve these situations we have come with a general solution that can also be applied to other problems into your program (2). The solution is a garbage collector based on reference counting. This garbage collector is perfectly compatible with the well known retain/release policy from OpenStep.

The algorithm

The garbage collector neither maintains explicitly all the pointers in your program nor it collects all the memory allocated by you in the program. Instead it collects and maintains only some special kind of objects, that are garbage collectable.

The algorithm was inspired from a similar one found in the Brian M. Kennedy's <bmk@csc.ti.com> OATH C++ library. It works in three passes. Suppose that all the objects that are garbage collectable are known. Also each object has an additional flag, used for determining if the object was already visited.

During the first pass, all objects that are garbage collectable clears the associated flag and receive the message -gcDecrementRefCountOfContainedObjects. In this method the object decrements the ref count of every garbage collectable object it contains. After this pass all the objects that have the ref count 0 are part of cyclic graphs. Such objects have their ref count due only to another objects from graph.

In the second pass we have to restore the original ref counts and to isolate the nodes from cyclic graphs. In this pass all the objects that have the ref count greater than 0 receive the message -gcIncrementRefCountOfContainedObjects. In this method the object check the flag if it's set. This flag tells if the object was visited previously. If the flag is set, the method returns, else the flag is set. Then the ref count of every garbage collectable object contained is incremented and the message -gcIncrementRefCountOfContainedObjects is sent to those objects.

After this pass all the objects that are reachable from `outside' have their ref count greater than 0. All the objects that still have their ref count equal with 0 are part of cyclic graphs and there is no reference from `outside' to an object from these graphs.

In the third pass all the objects that have their ref count equal with 0 receive the -dealloc message. In this method the objects should send the -release message to all contained objects that are not garbage collectable. This because the order of deallocation is not known and you can send -release to an already deallocated object. So if a class contains both normal objects and garbage collectable objects, it should maintain their collectable status when the objects are retained.

The GarbageCollector class

The class GarbageCollector implements the garbage collector. It has the following interface: 

@interface GarbageCollector : NSObject

+ (void)addObject:(id)anObject;
+ (void)objectWillBeDeallocated:(id)anObject;

+ (void)collectGarbages;

@end

A new garbage collectable object has to be made know to the GarbageCollector collector by sending it the +addObject: message with self as argument. When the object is deallocated it should inform the GarbageCollector class about this by sending it the +objectWillBeDeallocated: message with self as argument.

The +collectGarbages should be send to the GarbageCollector class to collect the garbages. You can send it whenever you want. If you are using a run loop in your program you can set a timer to be called periodically. Or you can call the garbage collector when the program is idle.

In the current implementation the garbage collector is not thread-safe, so please don't use it in multi-threaded programs, unless you use garbage collectable objects only in one thread.

The GarbageCollecting protocol

To allow instances of a class to be garbage collectable, the class should implement the following protocol: 

@protocol GarbageCollecting

- gcSetNextObject:(id)anObject;
- gcSetPreviousObject:(id)anObject;
- (id)gcNextObject;
- (id)gcPreviousObject;

- (void)gcIncrementRefCount;
- (void)gcDecrementRefCount;

- (void)gcDecrementRefCountOfContainedObjects;
- (BOOL)gcIncrementRefCountOfContainedObjects;

- (BOOL)isGarbageCollectable;

@end

The GarbageCollector class uses a double linked list to maintain the objects. The gcSetNextObject:, gcSetPreviousObject:, gcNextObject and gcPreviousObject are used by the collector to add or remove objects in its list. This could change in the future.

The gcIncrementRefCount and gcDecrementRefCount methods should increment, respectively decrement the ref count of receiver.

The gcDecrementRefCountOfContainedObjects method should decrement the ref count of all garbage collectable objects contained, by sending them the -gcDecrementRefCount.

The gcIncrementRefCountOfContainedObjects method should check the flag. If this is true, the method should return NO; it this is false the method should set it. Then it should increment the ref count of garbage collectable objects contained by sending them the -gcIncrementRefCount message. After this it should send the -gcIncrementRefCountOfContainedObjects message to the same objects. Then it should return YES.

The object should respond YES at the -isGarbageCollectable message if it is garbage collectable. The NSObject class responds NO to this message.

You should note the asymmetry between the gcDecrementRefCountOfContainedObjects and gcIncrementRefCountOfContainedObjects methods. This makes the algorithm to work. So be careful if you're using copy/paste operations to write them in your editor :-)!

Support classes

There is a class GCObject from which you could inherit your own classes. This class implements the GarbageCollecting protocol.

Using this class, you could write a class whose instances hold other objects. This class is safe to cyclic references. Here is its implementation: 

@interface MyGCObject : GCObject
{
    id object;
    BOOL isGarbageCollectable;
}

- (void)setObject:(id)anObject;
- (id)object;

@end

@implementation MyGCObject

- (void)setObject:(id)anObject
{
    [anObject retain];
    [object release];
    object = anObject;
    isGarbageCollectable = [object isGarbageCollectable];
}

- (id)object
{
    return object;
}

- (void)decrementRefCountOfContainedObjects
{
    [object gcDecrementRefCount];
}

- (BOOL)incrementRefCountOfContainedObjects
{
    if(![super incrementRefCountOfContainedObjects])
        return NO;
    [object gcIncrementRefCount];
    [object incrementRefCountOfContainedObjects];
    return YES;
}

- (void)dealloc
{
    if(!isGarbageCollectable)
        [object release];
    [super dealloc];
}

@end

There are also concrete subclasses of NSArray and NSDictionary named GCArray and GCDictionary respectively, together with their mutable classes GCMutableArray and GCMutableDictionary. Their instances could hold both normal and garbage collectable objects.

If you don't want to write your own Application Object you can use the GCGenericRecord class that is similar with EOGenericRecord but works correctly in case of cycles.

When do I need garbage collectable objects?

The algorithm is not working if the cycles is interrupted in one place. So to assure it works correct you'll have to make all the objects part of a cycle to be garbage collectable.

An object that is garbage collectable behaves like a normal object with respect to retain/release messages, so it will be deallocated as usual if it is not part of a cycle. The only overhead implied is that it will participate in the garbage collection algorithm if one occurs while the object is alive.
