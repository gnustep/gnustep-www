Writing a New Adaptor

GDL comes with written adaptors for Sybase, Microsoft SQL Server and PostgreSQL databases. Other database servers can be supported as well if adaptors are written for them. You should read this chapter if you intend to write a new adaptor.

To create a new adaptor you usually need to implement some concrete subclasses of EOAdaptor, EOAdaptorContext and EOAdaptorChannel. If the SQL language understood by the database server you will also have to subclass EOSQLExpression.

In the rest of this chapter are presented the methods that you usually need to implement in the adaptor subclasses and a description of EOSQLExpression.

EOAdaptor

You usually have to implement the following methods of EOAdaptor:

- (Class)expressionClass
the SQL expression class used to generate the database operations (default is EOSQLExpression)
- (Class)adaptorContextClass
the adaptor context class (default is EOAdaptorContext)
- (Class)adaptorChannelClass
the adaptor channel class (default is EOAdaptorChannel)
- formatAttribute:(EOAttribute*)attribute
returns an EOExpression object that can be used as a table name in SQL expressions. The default implementations sends the expressionValueForContext: message to attribute.
- formatValue:value forAttribute:(EOAttribute*)attribute
returns a value that can be used in SQL expressions. The adaptor should perform any additional character escaping needed the database server. The default implementation sends to value the expressionValueForContext: message. You should not make this formatting by writing categories to classes, because if one uses several adaptors at the same time the methods conversion methods will be overwritten each other.
- (BOOL)isValidQualifierType:(NSString*)typeName
returns YES if values of type typeName can be used in qualifiers

The EOAdaptor class also maintains the model and the connection dictionary. A new adaptor should decide what are the information needed to create a new database connection and require them to be specified in the connection dictionary.

EOAdaptorContext

The EOAdaptorContext represents a transaction scope within database server. An important issue you have to take into consideration is whether several channels can be opened or not within the same transaction. Some database servers such as Sybase allow only one channel for example. If this is the case with your server you have to verify the programmer does not create more than one channel per context.

The methods you have to implement are those that begin, commit and rollback a transaction since these methods in EOAdaptorContext simply return NO.

- (BOOL)primaryBeginTransaction
opens a new transaction and returns YES if the action was successful
- (BOOL)primaryCommitTransaction
commits the transaction that is currently opened and returns YES if the action was successful
- (BOOL)primaryRollbackTransaction
rollbacks the transaction that is currently opened and returns YES if the action was successful

These are the so called "primary" methods because they do only the basic operations and do not take any actions, by calling the delegate for example, when the operation succeed or failed. Of course you can implement in your subclass the top methods but then you have to implement the whole behavior they have.

Another important method is

- (BOOL)canNestTransactions

that should return YES if transactions can be nested.

EOAdaptorChannel

Subclassing the EOAdaptorChannel is the most difficult part in writing a new adaptor. This class contains almost the all code dependent on database server. The database client library can simplify a lot this task if it provides all the information you need.

The things you have to know before you start to write any line of code are the following:

  • what are the types supported by the database and how do they map to Objective-C classes. The GDL existing adaptors use categories to the usual Foundation classes to create the object values or obtain the database value from an object.
  • how to retrieve a value of a given type after the fetch request was made. If all the types are supported in a uniform manner, e.g. there is only one way to access all the values no matter what is their type, then the task is simplified. Some database client libraries for example make a distinction between elementary types (such as characters, integers and floats) and large data (also known as BLOB or binary data).
  • how to evaluate an arbitrary SQL expression (using evaluateExpression:) that could possibly contain more than one request. Such an evaluation implies that you should be able to find out of what kind were the requests from the original expression.
  • if an arbitrary fetch request was evaluated using evaluateExpression: the library has to tell what were the attributes involved in request.
  • you have to be able to find out what are the tables from the database the adaptor is connected to. For each table you also have to find out what are the columns and their types.

The methods you have to override in your concrete subclass of EOAdaptorChannel are:

- (NSMutableDictionary*)primaryFetchAttributes:(NSArray*)attributes
withZone:(NSZone*)zone
Fetch the attributes specified in the attributes array that contains the EOAttribute objects. The method should return a dictionary having as key the name of the attribute (not the attribute itself) and as value an object whose class is specified in the attribute and whose value was retrieved from the database. The objects should be allocated from zone. This methods advances to the next record retrieved. If no more records follow this method should return nil otherwise the dictionary row should be returned.
- (BOOL)evaluateExpression:(NSString*)anExpression
Evaluates the arbitrary SQL expression specified by anExpression and returns YES if the evaluation succeeds or NO otherwise.
- (NSArray*)describeResults
Returns an array of EOAttributes corresponding to the last fetch operation sent to the database. The attributes returned should not necessary exist in the model. Each attribute should have at least a name and the external type specified. The result is undefined if the last request was not fetch request.
- (EOModel*)describeModelWithTableNames:(NSArray*)tableNames
- (NSArray*)describeTableNames
- (BOOL)readTypesForEntity:(EOEntity*)anEntity
- (BOOL)readTypeForAttribute:(EOAttribute*)anAttribute
These methods are used to determine a model from the meta-information stored by the database. If these information is not available you can not implement these methods.

You may also need to implement the following methods if the database client library does handle differently the database types:

- (BOOL)insertRow:(NSDictionary*)aRow forEntity:(EOEntity*)anEntity
- (BOOL)updateRow:(NSDictionary*)aRow
describedByQualifier:(EOQualifier*)aQualifier
- (BOOL)deleteRowsDescribedByQualifier:(EOQualifier*)aQualifier

Special care should be taken in implementing these methods; they should return NO if no record was affected by the operation, so if the database client library does not provide you this information you have to execute a fetch operation before to find out the number of affected rows.

EOSQLExpression

If the SQL language understood by your database server has some small variations to the SQL language generated by GDL, you may also need to write a subclass of EOSQLExpression, the class that is responsible with the SQL operation generation. Usually you need to do this to support locks in SELECT operations.

EOSQLExpression has four subclasses that are used for SQL generation:

  • EOSelectSQLExpression
  • EOUpdateSQLExpression
  • EOInsertSQLExpression
  • EODeleteSQLExpression

The EOSQLExpression class has four methods that return the subclasses used to generate an expression:

  • + (Class)selectExpressionClass
  • + (Class)insertExpressionClass
  • + (Class)deleteExpressionClass
  • + (Class)updateExpressionClass

To customize a particular SQL operation you have to follow these steps:

  • create a subclass of EOSQLExpression, lets say it EOCustomSQLExpression
  • create a subclass of the class corresponding to the operation you want. For example if you want to modify the SELECT operation then you have to subclass from EOSelectSQLExpression. Let's name this class EOCustomSelectExpression.
  • implement the selectExpressionClass method of EOCustomSQLExpression to return the EOCustomSelectExpression.
  • implement the method you need to the EOCustomSelectExpression class.
  • implement the expressionClass method to your custom EOAdaptor class to return the EOCustomSQLExpression.

This way your adaptor classes will use your custom EOSQLExpression to generate SQL expressions.
