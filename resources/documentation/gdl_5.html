The Database Level

The Database Level main purpose is to offer an Object Oriented access to a relational database maintained by a specialized SQL data server like Sybase, Informix or Oracle. The Adaptor Level manipulates data as rows (NSDictionary instances) from tables while the Database Level uses Application Objects (instances of user defined classes) that store the row data, implement user defined behavior and automatically resolve relationships.

The Database Level uses the Adaptor Level to perform its operations with the SQL data servers. For users that need not concern about working with the Adaptor Level, Database Level objects hide the Adaptor Level by creating and using the Adaptor Level objects they need. However, users that want to perform low level operations available only in the Adaptor Level, can access these objects and work with them as usual.

Its main features are:

  • operates in terms of Application Objects compared to the Adaptor Level that operates in terms of rows (NSDictionary instances).
  • provide an uniform access to Application Objects properties through the EOKeyValueCoding informal protocol (category of NSObject).
  • mapping from rows to Application Objects and back from objects to rows.
  • uniquing of rows based on primary keys, so that multiple fetches of the same row go to the same object.
  • delayed relationship resolution.
  • provide several strategies to lock objects into the data server for update operations by using the dataserver locking features or by using snapshots (the latest known state of a row).
  • creation and management of Adaptor Level objects; for operations not available in the Database Level users can access the adaptor objects and work with them.

Database Introduction

This section provides an introduction to the features of the Database Level. Some of these features are fully explained in section Database Features.

Database Classes Introduction

The Database Level is made of four classes:

EODatabase
It represents the database maintained by the SQL data server. It holds the uniquing dictionary that maps primary keys to objects in memory and the snapshots for all objects fetched from the data server outside any transaction. A EODatabase object owns an EOAdaptor object that is used to access the model for the database. EODatabase objects can have several EODatabaseContext objects to manage concurrent transaction scopes.
EODatabaseContext
Controls a transaction scope with the SQL data server. It owns a corresponding EOAdaptorContext and can have several EODatabaseChannel objects to actually perform the operations with the SQL data server. It also controls the locking strategy used to lock objects in the data server, keeps uniquing and snapshot dictionaries until the transaction is committed and handles nested transactions.
EODatabaseChannel
Used to actually perform fetch, insert, update, delete and lock operations with the SQL data server. It owns a EOAdaptorChannel object that is used to perform all the operations.
EOGenericRecord
The generic Application Object class. It implements an object that remembers its entity and keeps its properties as a NSDictionary.

Uniform properties access

The Database Level uses objects from user defined classes to hold data fetched as rows from the data server. These classes might have different properties (attributes) accesible through accessor methods returning or taking as argument different types, but the Database Level must be able to access them both in writing and reading in an uniform manner.

Writing is necessary when the object is fetched or refetched from the database and values in the row are to be tranfered to the object (see section Mapping from rows to objects). Reading is needed when the object is about to be inserted or updated into the data server, when its properties must be assembled into a row (NSDictionary instance) used in Adaptor Level operations.

Access to all the object properties is implemented in the EOKeyValueCoding category of NSObject, which implemets the access to the properties by name instead of accessor methods. 

@interface NSObject(EOKeyValueCoding)

-(BOOL)takeValuesFromDictionary:(NSDictionary*)dictionary
-(NSDictionary*)valuesForKeys:(NSArray*)keys

@end

Setting properties is performed through takeValuesFromDictionary:. This methods uses the keys in the dictionary argument to name the properties and their corresponding values as the values to be set.

Getting values for properties from objects is done through valuesForKeys: method. Its keys argument is an array of properties names and its return value is a NSDictionary with the the properties names as keys and their corresponding values taken from the receiver as values.

Normally users will not want to implement these methods and will use the default ones. Classes that implement these methods are NSObject, NSDictionary class cluster and EOGenericRecord.

NSObject implementation attempts to use existing accessor methods or instance variables to access properties by name and performs a large set of type conversions to and from standard C types and OpenStep value objects (NSString, NSNumber).

To access the properties valuesForKeys: does the following for each key in keys argument (example property name: salary)

  1. If the receiver has a method `key' then that method is invoked and its result (`value') is inserted in the returned dictionary under the key `key' (example methods -(id)salary, -(int)salary). If the method does not return an object type then type conversions are made.
  2. If the receiver has an instance variable named `key' then the `value' contained in inserted in the returned dictionary under the key `key' (example instance variable: int salary). If the instance variable does not return an object type then type conversions are made.
  3. If the receiver has no method or instance variable named `key' then the returned dictionary will contain no key--value pair for the key `key' (example: returned dictionary will have not salary key).

key is expected to be NSString. If the method does not return an object type then its result is converted to NSString for char* and to NSNumber for other integer C types (char, unsigned char, short, unsigned short, int, unsigned int, long long, unsigned long long, float, double).

To set properties takeValuesFromDictionary: does the following for each key--value pair in dictionary argument (example property name salary with a value of 100):

  1. If the receiver has a method `setKey:' then that method is invoked and with the value as argument. For example for -(void)setSalary:(NSNumber*) method definition 
    [object setSalary:value]
    is invoked, and for -(void)setSalary:(int) method definition 
    [object setSalary:[value intValue]]
    is invoked. If the method's argument is not an object type then the value is converted to the appropriate type.
  2. If the receiver has an instance variable named `key' then it is assigned the value. For example for id salary variable definition 
    [salary autorelease]; 
salary = [value retain]
    is executed and for int salary variable definition 
    salary = [value intValue]
    is executed. If the instance variable's type is not an object type then the value is converted to the appropriate type.
  3. If the receiver has no `setKey' method or key instance variable then the method does nothing.

key is expected to be NSString. If the argument of `setKey:' is not an object the value from the value object is converted to the corresponding C type; for char* the value is sent stringValue to convert it in NSString then it uses cString and for (char, unsigned char, short, unsigned short, int, unsigned int, long long, unsigned long long, float, double) value is treated as a NSNumber. If an attempt is made to convert EONull value to an C type then the object is sent unableToSetNullForKey:key message.

Mapping from rows to objects

The main feature of the Database Level is to map rows fetched by the Adaptor Level to Application Objects and to pack properties from the Application Objects into rows for INSERT and UPDATE operations. The mapping operations are performed by the EODatabaseChannel instances as they fetch, insert or update objects.

When inserting (updating), the database channnel uses the following algorithm:

  1. Determine the entity for the application object (referred as object). If the object responds to entity then the object is sent entity. Else the model is sent entityForClass: with the object's class as an argument.
  2. Send the object valuesForKeys: to get the values the channel must insert (update). The properties names are the names of the class properties attributes in the object's entity.
  3. Perform adaptor INSERT (UPDATE) operation.

When the database channel is fetching objects from a given entity (called current entity) it performs the following steps: (see section Database Features)

  1. Use the EOAdaptorChannel to fetch a row (a NSDictionary instance) from the data server.
  2. Use the uniquing (see section Uniquing) mechanism to determine to which application object the values are to be transfered. If no object is found then a new one is created, based on the class for the current entity. The new object is initialized with initWithPrimaryKey:entity: if it responds to this message else it is sent init.
  3. Create fault objects for the object's relationships based on the values in the fetched row (see section Resolving relationships).
  4. Sends the object takeValuesFromDictionary: with a dictionary that contains the key--value pairs for class properties attributes and relationships.
  5. Sends the object awakeFromDatabaseChannel: with self as an argument.

Uniquing

In most applications it is required that no matter how many times a certain row is fetched the data to be transfered in the same application object, thus using less memory and keeping objects syncronized.

For example, in an application that lets the user edit person records the person inspector displays the department name. Suppose that there is one person inspector opened. To display the department name and location the Control Level must get the department object for the person, so it fetches the object for the department. If the user opens a department inspector for the same department, to edit the department location, the Control Level fetches the same department again. If no uniquing is made there are two objects for the same department. This brings the system in an inconsistent state besides the fact that is uses more memory than necessary. With uniquing, when the department is fetched again, the same object is returned, so there is only one object corresponding to one row in the database.

For uniquing to be operational the library must be able to distinguish among records from an entity (actually from a table in the data server). This is accomplished by defining a primary key for the entity. The primary key is a set of one or more attributes (usualy columns in the entity's table) that identify rows in an unique way.

For example, for a Person entity, if persons are identified by a person id, each person with a unique id, an personId attribute corresponding to the person_id column in the PERSONS table could be defined and set as the primary key attribute for the Person entity.

When a row from an entity is fetched, its corresponding primary key is computed by sending the entity 

[entity primaryKeyForRow:theRow]

message, which returns a NSDictionary containing the primary key for that row (primary key attributes as keys and the corresponding values from the theRow.

Uniquing is controlled by the EODatabase and EODatabaseChannel objects. The EODatabase maintains a uniquing dictionary that has the entity and primary key pairs as keys and their corresponding Application Objects as values. This dictionary does not retain the Application Objects, so Application Objects must call the forgetObject: from the EODatabase class when they get deallocated. This gives the EODatabase objects a chance to remove that object from the uniquing dictionary. If this dictionary is not updated when the object is deallocated, the first time the object is fetched, the system will find some object under that primary key and try to set the values fetched into an deallocated object.

During transactions, the EODatabaseContext keep a stack of uniquing dictionaries for each nested transaction. When the transaction is committed the uniquing information is folded in the parent transaction uniquing dictionary on in the database context's EODatabase.

By default the EODatabase uniques objects, but this behavior can be controlled through 

-(void)setUniquesObjects:(BOOL)flag

and cannot be changed while the database has open channels.

When uniquing is in effect, while fetching, the EODatabaseChannel after getting a row from the EOAdaptorChannel, computes the primary key for that row and asks the database context and database for the object for that primary key. If an object is already registered, values will be set in that object, and if no object is registered the channel create one (see section Mapping from rows to objects) and records it in its context uniquing dictionary.

Resolving relationships

Another key feature of the Database Level is the automatic relationship resolving. Sometimes one or more attributes in one row form a primary key for a record in some other entity (see the Model an the Relationships chapter). If someone is working at the Adaptor Level he has to fetch the objects described by the relationship explicitly. When working at the Database Level when the EODatabaseChannel is fetching an object from an entity it uses the Adaptor Level to fetch the attributes the entity has, then it resolves the relationships defined for that entity. The objects pointed by the relationships are added to the dictionary with the object's properties and set in the object with the takeValuesFromDictionary: method.

When resolving relationships the EODatabaseChannel does not fetch the objects pointed by the relationship immediately. Instead of fetching them immediately it creates some stand-in objects, called faults. These faults behave like the real objects until they are sent a message that they cannot handle, when they fetch the data from the database. When a fault object is sent a message it cannot handle, it fetches the data it represents and transforms the fault into the real object.

There are two kind of faults created by the library: to-one faults for to-one relationships and to-many faults for to-many relationships. To-many faults represent NSArray objects, and are described by the destination entity and the qualifier they will use to fetch. To-one faults can represent any class that is used for Application Objects and are described by the destination entity and the primary key for the object. To-one faults are handled in a special way regarding to uniquing. As to-one faults represent objects they are registered in the uniquing dictionary under the primary key for the entity; before attempting to create a to-one fault the EODatabaseChannel looks up in its EODatabaseContext and EODatabase for an object from the destination entity with the same primary key and if one is found it uses that object instead of creating a fault (see section Uniquing).

Relationships are not fetched immediately for two reasons. First the channel that performs the fetch is busy fetching so it cannot handle another fetch. Second, with the delayed fetching the application is speeded up because it will fetch the objects as it needs them, not all at once.

The relationship resolution mechanism has one disadvantage because of the retain--release mechanism in the Foundation Library. If relationships are defined so that retain cycles appear (a person has a to-one relationship to his boss and the boss has to-many relationship to his employees) and objects never get deallocated. To overcome this problem the library uses a Garbage Collector (see Garbage Collector).

Users can create faults themselves using EOFault class methods. When faulting a to-one fault, if the entity and primary key do not describe one and only one object an EOUnableToFaultToOneException exception is raised.

Transactions, locking and updating objects

One of the most difficult to understand and to work with chapter in databases are transactions and record locking for updates. Transactions are used in database operations to specify a set of operation that will either succeed all of them of fail all even if only one cannot be executed. This is needed to insure database integrity, i.e. not to leave the database in an inconsistent state if one operation fails. Locking is needed to handle concurrent access to the database maintained by the data server. For example if one user is about to update a record he must lock that record first then perform the update; the record will be eventually unlocked when the transaction it was lock in is committed or aborted. If the user does not lock the record, a second user might update that record in between. The first user is not notified in any way that the record he is about to update has just been updated by someone else. If the secod user attemps to update the record locked by someone else the data server issues an error and the record is not updated.

An example can be automatic key generation. Say the table KEYS has two columns, name and maxkey, first representing a product name and the other the current unassigned serial number for that product. Whenever a product is added into the database we want to assign it a unique serial number so we must get the current unassigned serial number and then increment it. 

BEGIN TRANSACTION
SELECT maxkey 
    FROM KEYS HOLDLOCK 
    WHERE name = 'product name';
UPDATE TABLE KEYS 
    SET maxkey = maxkey + 1
    WHERE name = 'product name';
COMMIT TRANSACTION

To lock the record in the data server between the SELECT and the UPDATE operation the HOLDLOCK clause is used.

To lock an object (or its corresponding record into the database) outside any transaction the users must buid their own locking server, perhaps using the distributed objects mechanism built into the Foundation Library.

The Database Level offers some fetures to automatically handle and control locking and update operations in transactions and outside them. The EODatabaseContext defines the locking strategy to be used in update operations, for all updates performed by the context's channels. It also remembers objects explicitly locked during a transaction with the EODatabaseChannel lockObject: method.

The locking strategies used for updates are:

EOUpdateWithPessimisticLocking
The EODatabaseChannel will require that an object be locked in the current transaction for an update to procedd. If the object given to updateObject: is not registered as locked in the channel's context the channel uses the EOUpdateWithOptimisticLocking strategy.
EOUpdateWithOptimisticLocking
Uses snapshots (last known state of the database record) for rows to check that the record has not changed since it was last fetched. If the values in the snapshot differ from those in the database or there is no snapshot registered in the channel's context or database the operation fails.
EOUpdateWithNoLocking
The EODatabaseChannel will blindly perform update operations. Objects need not be locked into the database and snapshots are not used in update operations to check that the recoed was not modified.
EONoUpdate
Under this strategy the context's chanels will fail on updateObject:. This strategy, combined with snapshotting turned off in the context's EODatabase may be used to consult databases in a read only fashion without snapshotting overhead.

Snapshots are the last known values for attributes from a row. In the model for a database, users can define attributes used for locking, i.e. attributes whose values will be kept in snapshots. Snapshots are recorded in the EODatabaseContext while in a transaction when objects are fetched or inserted and are transfered in the context's database then the top level transaction is committed. The EODatabase can be configured wether to keep snapshots between transactions or not.

Keeping snapshots between transactions has the advantage that an object fetched in a transaction already committed need not be refetched to make other snapshots.
