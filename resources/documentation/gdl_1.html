Introduction

Programs that need to access a database may use the library provided by the database vendor to send commands and retrieve the results from database. This aproach is adequate for small programs. If you intend to write a big program you usually create another layer on top of this database library. The purpose of this layer is to transform the details of lower level programming into some higher abstractions that are more appropiate for your application. For example if you write an object-oriented application you may want to pack the data in objects.

If the program is large you access the same tables from different parts of the program then several objects containing the same data will appear. These objects should be kept consistent with each other or paradoxes in data values will appear in program. This means that at every modification of the data should be made in all the objects that contain it.

Some other abstractions can be imagined further. For example if your program has a windowing interface, a common method of displaying data is in what is called a master-detail view. Suppose you have a table in which you display department names and when you select one of them, all the persons that are in that department appear in another view. By creating such a paradigm you can reuse it in all the parts of your program that use it.

On top of this last abstraction you can further create other abstractions that are specific to your application. By structuring your application in such layers of abstractions you can create a much more robust application than if you write it using directly the database access library. In addition your application becomes easy to extend with new features and of course much more easy to maintain.

The GNUstep Database Library (GDL) offers you a well structured way to build your application. It maps the database records into your own objects, it automatically maintains them uniquely throughout your program and helps you to create control layer abstractions using master-details views and undo engines for the interface interaction. GDL is database independent; you can use any database you want if you have an adaptor for it. GDL does not come with a database server nor it is a database server, but it has a clearly defined adaptor level which communicates with specific DBMS.

GDL is structured in several levels that provide increasing higher of abstractions. You can program your application at whatever level you need; the library does not impose you any restriction on this. Usually you may need to program at the lower levels only when the higher levels don't offer you the functionality you want.

Application Objects

Let's imagine a simple human resources application to be written. We have a set of people, presumably employees, and we have some personal and company-related data associated with each person. An example of such data would be the person's last name, first name, and the department in which they work.

When writing database programs, it is desirable to design the program based upon the business processes and the flow of information through your organization. This design is independent upon how data will be physically stored and how it will be displayed to the end-user. The GDL uses the concept of Application Objects to create a model of your business information that closely corresponds to your business processes; then you create a mapping from your application objects to the actual database data. The point of this approach is easy to see; programs can be designed and implemented based upon the needs of the business, and underlying changes in the physical database storage is easily handled by adjusting the mapping; leaving your business model intact.

The above example involves two Application Objects: the Person and the Department. In section The Model, you will see how the model of your Application Objects is created, and how they are mapped to the physical datastore.

The Access Layer

GDL comes with a powerful datasource and related classes designed to be used use with relational databases. This layer consists of the following:

  • The adaptor level maps the records from the database into dictionaries. This is the lower level of abstraction and it is dependent on the database server you use.
  • The database level creates Application Objects from the dictionaries received from the adaptor level.
  • The model is used by the adaptor and database levels to store information about how the records should be mapped into Application Objects.
  • The database datasource is a concrete implementation of the datasource protocol for relational databases.

The Datasource

Application Objects are retrived from and stored to a datasource. The datasource is a source for Application Objects, either new ones -- fresh new object created at your request -- or for old ones -- ones that you've created and used in the past and then you've saved for a later use.

The datasource is an abstract interface; it does not specify anything about the support used to store the Application Objects persistently. You can imagine several different supports used for different types of datasources: databases, flat files, DBM files or anything else that can be used to store data persistently.

The datasource interface does provide only methods for creating new objects, inserting, deleting, updating and retrieving them from the persistent support.

The GNUstep Base Library and the GNUstep Database Library

The classes in the GNUstep Database Library are based upon and heavily utilize the classes in the GNUstep Base Library. The GNUstep Base Library is a large collection of Objective-C classes that encapsulate fundamental datatypes like strings, numbers, date and time; it also contains numerous general purpose data structures like arrays, dictionaries, and sets. For complete information about rhe GNUstep Database Library please See section `Introduction' in The GNUstep Base Library Manual.

The classes must used by the GNUstep Database Library are:

NSArray
An ordered list of objects.
NSCalendarDate
Date and time objects with time zone information.
NSData
Encapsulation of an arbitrary block of binary data.
NSDictionary
Collection of key-value pairs.
NSNumber
Encapsulation of C scalar datatypes like float, double, and integer.
NSString
Encapsulation of character strings.
